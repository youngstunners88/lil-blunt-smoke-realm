Accessibility Statement

Last updated: 4 September 2026

This page says plainly what has and hasn't been checked for accessibility on this site. It is not a compliance claim — no formal audit against a standard like WCAG has been performed, and this page will say so honestly rather than assert a certification that doesn't exist.

What this covers

This statement covers the website — this hub and its static pages (About, How to Play, the FAQ pages, Terms, Privacy, and this page). It does not cover the game itself, which has a different, more limited accessibility surface — see below.

What has been checked

This was a source-code review of the site's components, not a screen-reader walkthrough. Four things were verified directly against the code:

  • Image alternative text. Every <img> element in the site's component source carries a populated, descriptive alt attribute — for example the character portrait's alt text names the character and describes the scene, rather than repeating a filename or leaving the attribute empty.
  • Icon-only controls. The background-music toggle button has no visible text label, so it carries an aria-label that switches between "Play background music" and "Pause background music," plus an aria-pressed attribute that tracks its current state for assistive technology.
  • Keyboard operability. Interactive elements use the CSS :focus-visible pseudo-class rather than suppressing the outline entirely, so a keyboard user sees a ring around whichever control currently has focus while a mouse click does not trigger the same ring. The in-app content overlay attaches a keydown listener for the Escape key and calls its close handler when that key fires.
  • Heading structure. Each static page uses a single h1 followed by h2 section headings in document order, rather than skipping levels or using styled paragraph text to fake a heading.

What has not been checked

Named specifically, not summarized away, because a code review is not the same evidence as using the site with assistive technology:

  • No manual pass with an actual screen reader — VoiceOver, NVDA, or JAWS — has been performed on any page.
  • Color contrast has not been measured with a contrast-ratio tool against every foreground/background color pairing the dark theme uses.
  • The in-app content overlay does not currently trap keyboard focus while it is open: a keyboard user can tab past the overlay's content into the page sitting behind it. This was found during this review and is listed here rather than fixed silently and left unmentioned.
  • No formal audit against WCAG 2.1, WCAG 2.2, or any other named standard has been run, so no conformance level — A, AA, or otherwise — is claimed anywhere on this site.

How the site is built, and why that matters here

The marketing hub is a React single-page application, but the pages this statement lists by name — About, How to Play, the FAQ pages, Terms, Privacy, and this page — are separate static HTML documents served directly, not rendered by JavaScript after the fact. That means a screen reader, a text browser, or a search crawler reading this page gets the same markup a sighted browser user gets, with no client-side rendering step in between. The React app layers an in-app overlay on top of these same documents for users who click through from the homepage, which is the overlay referenced above.

What would close the gaps above

In priority order, based on what this review found: add a focus trap and an initial-focus target to the content overlay so keyboard focus cannot leave it while open, and restore focus to the triggering element on close; run an automated contrast check against the site's dark color tokens and adjust any pairing that falls under a 4.5:1 ratio for body text; and complete one manual pass with a screen reader across the homepage and the static pages before considering any WCAG conformance claim. None of this has shipped yet — it is listed here as the concrete next step, not as work already done.

The game itself

Lil Blunt: The Smoke Realm is a 2D platformer rendered to a canvas and controlled entirely by keyboard — see the controls FAQ. Like the great majority of browser and console platformers, it is not operable by screen reader and requires a keyboard; there is no alternative input method in the current build. This is a real limitation of the medium, not something this statement will paper over.

Reporting a problem

If something on this site is hard to use with a keyboard, a screen reader, or any assistive technology, say so — through the same channels linked in the site footer (X or Telegram). This project has no company, office, or postal address to list; those are the real, checked channels the site already publishes.
